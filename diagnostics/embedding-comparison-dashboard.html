THE EXPERIMENT JOURNEY

What we changed, and what each experiment taught us

  1. Start with a million 1536d float32 vectors.

    The exact in-memory matrix occupied 6.144 GB. An early eight-query smoke test checked representation changes; it was too small to establish retrieval quality.

  2. Introduce a judged, reproducible 100-query sample.

    We downloaded official MS MARCO dev qrels and sampled 100 of the 1,780 queries with judged relevant passages in our first-million subset. The same query embeddings were cached and reused thereafter.

  3. Remove the hand-tuned 0.60 gate.

    On 1536d float32, removing this eight-example calibration raised Hit@5 from 41% to 46%, and Hit@10 from 54% to 64%. All primary comparisons below use unfiltered ranking.

  4. Reduce dimensions and change storage.

    1536d float32/float16: Hit@5 46%, Hit@10 64%. Truncated, normalized 512d float32/float16: 49% and 65%. MRR@10 fell from 0.346 to 0.321, so higher Hit@K did not mean uniformly better ranking. NumPy float16 saved memory but repeated conversion and normalization made it slower.

  5. Test K=5 versus K=10 before optimizing.

    At 512d float32, mean latency was 196.57 vs 193.77 ms. Full sorting did almost the same work either way; changing K alone did not provide a meaningful speedup.

  6. Replace full sorting with partial selection; test MLX.

    In one K=5 comparison: NumPy full sort 188.79 ms → NumPy partial selection 43.59 ms → MLX GPU float32 partial selection 31.80 ms. All 100 top-five result lists matched exactly in that run.

  7. Run native MLX float16.

    Same-run MLX float32 vs float16: 32.67 → 16.57 ms; 2.048 → 1.024 GB matrix. Hit@5/10 remained 49%/65%. Float16 preserved exact top-five order on 92/100 queries, with 99.2% average set overlap.

  8. Try 256d and find the quality tradeoff.

    The latest float16 comparison measured 512d at 16.16 ms and 256d at 8.69 ms. Matrix size halved again to 512 MB, but Hit@5 fell 49% → 41% and Hit@10 65% → 61%. We prefer 512d when keeping these hit rates matters.

FINAL DECISION

Choose 512d float16 on MLX for this workload.

For the retrieval-only stage, it is the fastest tested configuration that retains the observed 512d Hit@5 of 49% and Hit@10 of 65%, with a 1.024 GB vector matrix. The new optional cross-encoder reranker improves final Hit@5/10 to 59%/70% but adds about 314 ms per query; choose it only when that quality/latency tradeoff fits the application. The measured alternative at 256d wins on pure speed and memory, but gives up judged hits. Float32 at 512d retains the same hit rates while consuming twice the matrix memory and roughly twice the native MLX latency.

This decision prioritizes the observed hit rates, low latency, and memory together. Each benchmark is a local observation, not a production guarantee. The 100-query sample was reused while choosing configurations; a fresh held-out sample is needed to validate this choice. Concurrent load, exact boundary ties, total deployed website memory, and a production MLX backend have not been validated. All reduced dimensions were produced by local truncation and normalization, not new API embeddings.

CORPUS COVERAGE VS RANKING

Does using only one million passages explain our hit rates?

We search the first 1,000,000 of 8,841,823 passages in MS MARCO Passage Ranking v1 — about 11.3% of the collection, in archive order. This limits which general questions the corpus can answer.

For arbitrary queries

If the relevant passage is outside our subset, the retriever cannot find it. Expanding the corpus may improve answer coverage.

For these 100 benchmark queries

Every query was selected to have at least one official qrels-positive passage inside the current million. Missing all labeled answers from the corpus therefore does not explain these queries' misses.

Our primary metrics are Hit@5 and Hit@10: native MLX retrieval achieves 49% / 65%; reranking the top 100 achieves 59% / 70% on the same sample. These measure retrieval of judged passage IDs, not final answer accuracy. Some relevant passages rank too low, and some plausible answer-bearing passages are unjudged.

A larger corpus does not guarantee higher Hit@5 or Hit@10. It can add useful evidence and competing passages. Coverage and top-K ranking quality are different: their combined effect must be measured on the same queries. No experiment over all 8,841,823 passages has been run.

The eligibility filter found 1,780 dev queries with a judged positive in the first-million subset; we sampled 100 using a fixed seed. Results apply to that selected sample, not to all MS MARCO queries. Source: Microsoft MS MARCO dataset documentation.
